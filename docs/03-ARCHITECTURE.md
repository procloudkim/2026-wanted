# 03. 아키텍처 — 갱신 기준선

작성일 2026-09-18. 대상 제품: **갱신 기준선** — 공개 실거래 데이터로 전월세 갱신 조건의 위치를 계산해 보여 주는 웹 서비스.
이 문서는 결정마다 **Why(왜 이 선택인가) → What(무엇을 쓰는가) → How(어떻게 구성하는가)** 순으로 쓴다. 설계 제약의 출처는 `decisions/01-idea-selection/round2-data-first/research/` 의 실측 문서다.

한 문장 요약: **판정은 코드가 하고 서술은 LLM이 한다. 판정에 필요한 숫자는 빌드타임에 고정되고, 런타임에는 정적 자산과 LLM 호출 하나만 남는다.**

## 2. Why — 아키텍처 원칙

### 원칙 1. 판정은 결정론이다

- **왜**: 판정 6종(법정 기한, 코호트 백분위, 표본 수, 5% 상한 금액과 초과 차액, 신규 시세 대비 차액, 환산 부담)은 전부 산술이다. 같은 입력에 같은 출력이 나와야 사용자가 그 숫자를 협상 자리에 들고 갈 수 있다.
- **무엇·어떻게**: 판정 경로에 LLM을 두지 않는다. LLM은 ① 자연어·붙여넣은 메시지의 구조화 ② 건물명 별칭 후보 제시 ③ 숫자의 재서술 ④ 통지 문안 초안, 네 곳뿐이다. 함수는 프런트엔드가 만든 숫자 딕셔너리를 받아 문장만 돌려주고, 문장 속 숫자가 딕셔너리와 문자열로 일치하지 않으면 그 문장을 버린다.

### 원칙 2. 런타임 외부 의존을 하나로 줄인다

- **왜**: 외부 호출이 늘수록 끊길 지점이 늘고, 공개 API 한도는 사용자 수에 비례해 소진된다.
- **무엇·어떻게**: 런타임 외부 호출은 **OpenAI 하나뿐**이다. 원천 API도 좌표·지도 서비스도 런타임에 호출하지 않는다. OpenAI가 끊겨도 판정은 그대로고 문장만 템플릿으로 바뀐다.

### 원칙 3. 데이터는 빌드타임에 고정한다

- **왜**: 원천은 262만 행이고 갱신은 하루 1회다. 요청마다 다시 계산할 이유가 없다. 기준일을 화면에 못 박으려면 기준일이 배포마다 하나여야 한다.
- **무엇·어떻게**: 수집·정규화·집계는 빌드 파이프라인 안에서 끝난다. `manifest.json` 하나가 기준일·행 수·채움률·집계 버전을 들고, 프런트엔드는 그 값을 상단 배너에 그대로 출력한다.

### 원칙 4. 비밀값은 서버에만 둔다

- **왜**: LLM 키를 브라우저에 두면 그 키는 공개된 것이다. 이 한 가지 이유로 정적 전용 호스팅이 탈락한다.
- **무엇·어떻게**: `OPENAI_API_KEY`는 Functions 런타임 환경변수로만 존재한다. 원천 API 키는 빌드 머신에만 둔다. `.env`는 커밋하지 않고 `.env.sample`만 저장소에 두며, 배포 환경변수는 호스팅 대시보드에서 설정한다.

### 원칙 5. 개인정보는 애초에 받지 않는다

- **왜**: 받지 않은 정보는 유출되지 않고 보관 정책도 필요 없다. 이 제품의 판정에는 개인 식별 정보가 필요 없다.
- **무엇·어떻게**: 입력은 자치구·법정동·건물명·전용면적·만기일·현 보증금·제시 조건뿐이다. 업로드 엔드포인트가 없고, 선택 기록과 알림은 브라우저 로컬에만 남으며, 붙여넣은 임대인 메시지는 구조화 직후 버린다.

### 원칙 6. 데이터가 모르는 것은 모른다고 끝낸다

- **왜**: 서울시 파일에서 단독·다가구 25.22%는 주소 필드가 비어 물건을 특정할 수 없고, 표본이 없는 코호트도 있다. 이 구간에서 추정치를 만들면 제품이 거짓말을 한다.
- **무엇·어떻게**: 집계 자산이 표본 수 `n`을 항상 포함한다. 화면은 `n`을 그대로 적고, `n < 3`이면 판정을 보류하며, 결과 0건은 "판정 불가"로 끝낸다. `n`을 감추는 렌더 경로를 두지 않는다.

## 4. How — 데이터 파이프라인

각 단계는 입력·처리·출력·검증 지점을 갖는다. 검증 지점을 통과하지 못하면 다음 단계로 넘어가지 않는다.

### 단계 1 — 수집

- **입력**: `DATA_GO_KR_SERVICE_KEY`(Decoding 키를 URL 인코딩해 사용), `SEOUL_OPEN_DATA_KEY`.
- **처리**: 국토부는 `LAWD_CD`(법정동코드 5자리) × `DEAL_YMD`(연월) 조합으로 반복 호출한다. 서울은 페이지 단위(1,000행)로 순회한다. 서울 엔드포인트는 HTTP 전용이므로 **서버(빌드 머신)에서만** 호출한다.
- **출력**: `raw/molit/<LAWD_CD>-<YYYYMM>.xml`, `raw/seoul/<page>.json`.
- **검증**: HTTP 상태와 응답 결과코드를 함께 본다. 200이어도 본문이 오류일 수 있다. 조합별 기대 행 수 하한을 두고 미달이면 재시도 큐에 넣는다. 중단 시점부터 재개 가능해야 한다.

### 단계 2 — 채움률 측정 (이 파이프라인에서 생략 불가)

- **왜 필요한가**: 초기 표본 조회에서 갱신요구권·종전 보증금이 공백으로 와 입력 위험을 의심했으나, 2026-09-18 국토부 4종 API 실측(360회 호출, 149,651행)으로 원인이 확인됐다. 그 행들은 **신규 계약**이었고 신규는 정의상 이 필드가 비어 있다(신규 행의 권리 기재 0.0%, 4개 유형 공통). **갱신 행의 종전 보증금 채움률은 99.56~99.98%**다. 따라서 이 단계는 "입력이 비었을 위험"이 아니라 **원천이 조용히 바뀌는 것을 잡는 회귀 감시**로 유지한다.
- **처리**: `useRRRight`, `preDeposit`, `preMonthlyRent`, `contractType`의 채움률을 **원천별·연월별·법정동코드별**로 센다.
- **출력**: `manifest.json`의 `fillRate` 블록.
- **검증**: 채움률이 직전 스냅샷 대비 기준치 이상 떨어지면 빌드를 실패시키지 않고 **해당 필드에 의존하는 판정 카드를 비활성 플래그로 표시**한다. 프런트엔드는 그 카드만 닫고 나머지는 그대로 낸다. 빌드를 죽이면 나머지 판정까지 같이 죽는다.

### 단계 3 — 별칭 정규화

- **왜 필요한가**: 2026-07-01 행정구역 개편으로 지자체명 표기가 섞였다(같은 파일 안에서 어순이 다른 사례까지 있다). 별칭 테이블을 적용하면 주소 매칭이 **91.7%에서 98.3%로** 오른다. 정규화 코드를 안 짜면 6.6%p가 조용히 사라진다.
- **처리·출력**: ① 지자체명 별칭 테이블 ② 자치구코드+법정동코드 → 10자리 결합 ③ 건물명 기계 정규화(공백·괄호·"아파트") ④ 기계 정규화로 안 붙는 건은 **수기 별칭 사전**. 두 출처 사이 단지명 불일치 543건은 기계 정규화로 추가 일치가 0건이었으므로 사전이 필수다. 별칭 테이블은 `aliases/`에 **입력 자산**으로 두고 버전을 고정한다.
- **검증**: 매칭률을 매 빌드 측정하고 직전 대비 하락하면 중단한다.

### 단계 4 — 중복 제거와 출처 병합

- **왜 이렇게 하는가**: 두 출처는 같은 신고 원천에서 갈라져 나왔고 불일치가 **0.044%**다. 따라서 독립 교차검증이 아니라 **보완 관계**로 쓴다. 한쪽에만 있는 건을 채우는 용도이지 서로를 검증하는 용도가 아니다.
- **처리·출력**: 조인 키 = 법정동코드(10) + 본번 + 부번 + 계약일 + 보증금 + 월세 + 면적(소수 2자리). 이 키는 **유일키가 아니다** — 같은 키에 층·동만 다른 별개 계약이 있다. 중복 묶음은 "동일 계약 후보"로 표시하고 집계 분모에서는 묶음당 한 번만 센다. 필드 값이 갈리면 결측이 적은 쪽을 채택한다.
- **검증**: 불일치를 카운트해 리포트에 남긴다. 값을 버리지 않는다.

### 단계 5 — 집계 스키마 생성

- **처리**: 코호트 키 = `자치구 + 법정동 + 건물명 + 전용면적 10㎡ 구간`. 코호트마다 `n`, 인상률 분위수(p10/p25/p50/p75/p90), 5% 초과 비율, 갱신요구권 사용/기록없음 두 집단의 `n`과 5% 초과 비율, 같은 코호트 신규 전세 보증금 중앙값과 그 표본 수만 남긴다.
- **원본 행은 출력하지 않는다.** 크기 때문이기도 하고, 개별 계약을 자산에서 다시 집어낼 수 없게 하려는 것이기도 하다.
- **검증**: `n = 0`은 자산에서 제외하고, `n < 3`은 남기되 판정 보류 플래그를 세운다. 서울 전체 상수는 `anchors.json`으로 뺀다.

### 단계 6 — 산출물 크기 관리

- **처리**: 코호트를 **자치구 25개 샤드**로 쪼개 사용자가 자기 자치구 하나만 받게 한다. 건물명 인덱스는 별도 파일로, 입력 자동완성과 별칭 후보 제시에 쓴다.
- **검증**: 샤드당 gzip 상한을 두고 초과하면 면적 구간을 병합한 뒤 그 사실을 manifest에 적는다. 파일명에 콘텐츠 해시를 넣어 불변 캐시를 건다.

## 5. How — 런타임 흐름

```text
 사용자              프런트엔드(정적)            Functions            OpenAI
   │ 만기일·주소·금액      │                        │                   │
   ├─────────────────────▶│ manifest / buildings   │                   │
   │                      │ cohorts/<자치구> fetch │  (외부 호출 없음)  │
   │                      │ 판정 6종 계산 ← 여기서 끝                    │
   │◀─────────────────────┤ 숫자·타임라인·배너 렌더 │                   │
   │                      │                        │                   │
   │ "문안 만들어 줘"(선택) │ POST /api/compose      │                   │
   ├─────────────────────▶│ {숫자 딕셔너리, 상황문} │                   │
   │                      ├───────────────────────▶│ 입력 검증 → 호출  │
   │                      │                        ├──────────────────▶│
   │                      │                        │◀──────────────────┤
   │                      │◀───────────────────────┤ 출력 검증 3중      │
   │◀─────────────────────┤ 통과: 문장 / 실패: 템플릿                   │
```

**함수가 하는 일**: 비밀값 보관, OpenAI 호출, 출력 검증층 3중 적용, 실패 시 템플릿 대체.

**함수가 하지 않는 일**:

- 판정 계산을 하지 않는다. 숫자는 이미 프런트엔드가 만들어 보낸 것이다.
- 원천 API를 호출하지 않는다. 사용자 요청과 공개 API 한도를 연결하지 않는다.
- 저장하지 않는다. 데이터베이스가 없고, 요청 본문을 로그에 남기지 않으며, 응답은 `no-store`다.
- 사용자를 식별하지 않는다. 세션도 쿠키도 없다.

**검증층이 세 겹인 이유**: 숫자가 틀리면 협상 자리에서 사용자가 틀린 숫자를 말하게 된다. 법 결론을 쓰면 서비스가 법률 자문이 된다. 입력에 없던 고유명사·날짜·금액이 등장하면 그것은 생성된 사실이다. 세 실패 양상이 서로 달라 한 겹으로는 못 막는다.

## 6. 배포 구성

### Why — Cloudflare Pages + Functions

- **왜**: 정적 호스팅과 서버리스 함수가 한 곳에서 무료이고 콜드스타트가 없다. LLM 키를 브라우저에 노출할 수 없어 함수가 반드시 필요하므로 정적 전용 호스팅은 애초에 후보가 아니다.
- **대안과 트레이드오프**: Vercel 무료 플랜은 기능이 충분하고 개발 경험도 더 매끄럽지만, 무료 플랜이 **비상업 용도로 한정**되어 제품의 장래 성격에 제약을 건다. 성격이 바뀌면 이전 비용이 생긴다.

### What — 산출물 (2026-09-18 실측)

```text
dist/
├── index.html                  화면 하나. 섹션 7개가 같은 판정 딕셔너리를 렌더한다
├── assets/
│   ├── app.css                 토큰 기반. 라이트·다크 두 벌
│   ├── app.js                  입력·모드 판정·렌더·로컬 보관
│   └── rules.js                판정 산술 7종. 순수 함수, 외부 의존 없음
└── data/
    ├── index.json              자치구 목록과 빌드 메타 (1.7KB)
    ├── anchors.json            서울 전체 상수 + 모수 문자열 (1.3KB)
    └── cohort/<자치구>.json × 25   코호트 + 건물 색인. 최대 270KB (gzip 39KB)

functions/
└── api/
    ├── _llm.js                 비밀값·공통 규약·검증층 (밑줄로 시작하면 라우트가 아니다)
    ├── parse.js                POST /api/parse
    └── draft.js                POST /api/draft
```

`functions/` 는 `dist/` 밖에 둔다. Pages 가 프로젝트 루트의 `functions/` 를 라우트로 올린다.

**실측 규모**: 원본 596,178행 → 전세→전세 갱신 85,691건 → 코호트 11,715개 + 건물 색인 5,908개. 자산 합계 3.2MB, **사용자 1인당 전송량은 자치구 샤드 1개 ≈ gzip 40KB**다. §8의 추정(1인당 150KB)보다 작다.

**캐시**: 파일명에 해시를 붙이지 않고 `manifest`/`index.json` 기준으로 관리한다. 자산이 하루 1회만 바뀌므로 해시 URL의 이득이 없고, 해시를 쓰면 색인도 매번 새로 받아야 한다.

### How — 환경변수

| 이름 | 어디에 두는가 | 필수 | 용도 |
|---|---|---|---|
| `OPENAI_API_KEY` | 호스팅 대시보드(런타임) | 필수 | 문장 생성 |
| `OPENAI_MODEL` | 호스팅 대시보드(런타임) | 선택 | 모델 고정 |
| `OPENAI_BASE_URL` | 호스팅 대시보드(런타임) | 선택 | 프록시·대체 엔드포인트 경유 |
| `DATA_GO_KR_SERVICE_KEY` | 빌드 머신 `.env`만 | 빌드 필수 | 국토부 수집. **Decoding 키를 URL 인코딩해 쓴다** |
| `SEOUL_OPEN_DATA_KEY` | 빌드 머신 `.env`만 | 빌드 필수 | 서울 수집 |

원천 API 키를 배포 환경에 넣지 않는 이유는 단순하다 — 런타임이 원천을 호출하지 않으므로 필요 없기 때문이다. 필요 없는 비밀값은 두지 않는다.

### 배포 절차

```bash
set -a; . ./.env; set +a
./scripts/test_all.sh                        # 키 없이 도는 검증 전부 (약 3초)
python3 scripts/build_assets.py              # 수집 → 집계 → 자산 게이트 → dist/data (약 3분)
npx wrangler pages dev dist                  # 로컬 확인. 함수 포함
npx wrangler pages deploy dist               # 배포
```

1. `manifest`/`anchors.json` 의 기준일이 바뀌었는지 확인한다. 그대로면 데이터가 갱신되지 않은 것이다.
2. 수집 로그의 `실패 N` 이 0인지 본다. 0이 아니면 `--retry` 로 그 조합만 다시 받는다. **429는 조용히 빠진다** — 실측에서 오피스텔 80개 조합(7개 자치구)이 통째로 누락된 채 자산이 만들어졌다.
3. 배포 후 확인 2개: 상단 배너의 기준일, `/api/draft` 가 키 없이도 `ok:true` 로 응답하는지.

## 7. 보안

- **비밀값 관리**: `.env`는 커밋하지 않고 `.env.sample`만 저장소에 둔다. 샘플에는 값이 아니라 발급처와 주의사항을 적는다. 배포 환경변수는 호스팅 대시보드에서 설정하고 저장소에 사본을 두지 않는다.
- **저장소에 넣지 않는 것**: `.env`, 원본 CSV/XML(`data/raw/`), 대용량 압축 파일, 내부 리서치 문서. 재현은 스크립트로 한다.
- **개인정보 미수집**: 입력 항목에 개인 식별 정보가 없다. 업로드 기능이 없다. 선택 기록·알림은 브라우저 로컬에만 남고 내보내기는 사용자가 실행한다. 붙여넣은 임대인 메시지는 구조화 직후 폐기한다.
- **외부 호출 경계**: 런타임 아웃바운드는 OpenAI 한 곳뿐이다. 함수로 나가는 요청 본문은 **코드가 만든 숫자와 사용자가 스스로 붙여넣은 텍스트**이며, 그 안에 식별 정보를 넣지 않는다. 좌표·지도 서비스는 쓰지 않으므로 그쪽 응답 저장 문제 자체가 발생하지 않는다.
- **입출력 검증**: 함수는 본문 크기 상한·필드 화이트리스트·숫자 타입 검사를 통과하지 못한 요청을 거부하고, 응답은 텍스트 한 덩어리로만 내보내 HTML을 그대로 삽입하지 않는다. 신뢰 경계의 검증은 간소화 대상이 아니다.

## 8. 용량과 성능

### 집계 자산 크기 (측정된 행 수에서 계산한 추정)

| 자산 | 산정 근거 | 추정 크기 | 전송(gzip 추정) |
|---|---|---|---|
| `cohorts/<자치구>.json` × 25 | 코호트 레코드는 키 + 분위수 5개 + 비율 3개 + 표본 수 몇 개 = 200~300B. 자치구당 1,000~1,500 코호트 가정 | 샤드당 0.2~0.4MB | 샤드당 60~100KB |
| `index/buildings.json` | 서울 아파트·연립 건물명 수천 개 × 약 40B | 0.2~0.3MB | 60~80KB |
| `anchors.json` | 서울 전체 상수 수십 개 | 수 KB | 수 KB |
| 합계(배포물 기준) | 25개 샤드 + 인덱스 + 앵커 | 5~10MB | 사용자 1인당 **1샤드 + 인덱스 ≈ 150KB** |

핵심은 총량이 아니라 **1인당 전송량**이다. 사용자는 자기 자치구 샤드 하나만 받는다. 원본 262만 행을 그대로 올렸다면 이 수치는 성립하지 않는다.

### 호출 한도와 소진 계산

| 원천 | 한도 | 전체 재구축 | 일일 증분 | 여유 |
|---|---|---|---|---|
| 국토부 15126474 | 개발계정 10,000건/일 | 서울 25개 법정동코드 × 24개월 = 600회(페이지 포함 최대 약 1,200회) | 25개 코드 × 최근 2개월 = 50회 | 재구축도 하루 한도의 12% 이내 |
| 서울 OA-21276 | 1,000행/호출, 매일 1회 갱신 | 262만 행 ÷ 1,000 = 약 2,623회 | 최근 접수분만 | 일일 호출 한도는 **미확인** → 파이프라인을 재개 가능하게 만들어 며칠에 걸쳐 나눠 받을 수 있게 한다 |

런타임은 원천을 호출하지 않으므로 **사용자 수가 늘어도 공개 API 한도는 소진되지 않는다.** 이 성질이 이 아키텍처를 고른 가장 실질적인 이유다.

### 캐시 전략

- 콘텐츠 해시가 붙은 자산(`app.<hash>.js`, `cohorts/<자치구>.<hash>.json`): 장기 불변 캐시. 데이터가 바뀌면 파일명이 바뀐다.
- `manifest.json`은 짧은 캐시(기준일이 바뀌면 프런트엔드가 새 해시를 알아야 한다), `index.html`은 재검증 필수.
- `/api/compose` 응답: `no-store`. 생성 문장은 사용자별로 다르고, 캐시할 이유도 없다.

## 10. 대안 검토와 기각 이유

| 구분 | 후보 | 기각·채택 이유 |
|---|---|---|
| 호스팅 | **Cloudflare Pages + Functions (채택)** | 정적과 함수가 한 곳에서 무료, 콜드스타트 없음 |
| 호스팅 | GitHub Pages 등 정적 전용 | 함수가 없어 LLM 키를 둘 곳이 없다. 원칙 4 위반으로 **즉시 탈락** |
| 호스팅 | Vercel 무료 | 기능은 충분하나 무료 플랜이 비상업 한정. 차선으로 남긴다 |
| 호스팅 | 자체 서버·VPS | 무료가 아니고 운영 부담이 생긴다. 이 제품에는 상시 프로세스가 필요 없다 |
| 데이터 저장 | **정적 JSON 샤드 (채택)** | 집계 결과는 배포마다 고정된 값이다. 고정된 값에 데이터베이스가 필요 없다 |
| 데이터 저장 | 서버리스 DB(SQLite/D1 계열) | 임의 쿼리를 열어 주지만 필요한 쿼리는 코호트 하나 조회다. 런타임 의존과 장애 지점만 늘어난다 |
| 데이터 저장 | 오브젝트 스토리지 + 런타임 조회 | 정적 자산과 같은 일을 하면서 함수 왕복만 추가된다 |
| 데이터 저장 | 관리형 Postgres 무료 티어 | 휴면·용량 정책이 붙는데, 262만 행을 넣어도 조회 패턴은 코호트 하나다. 과하다 |
| 데이터 저장 | 브라우저 내 분석 엔진(원본 직접 질의) | 원본 262만 행을 사용자에게 내려보내야 한다. 전송량·초기 지연 모두 불가 |
| 조회 방식 | **빌드타임 집계 + 정적 조회 (채택)** | 사용자 수와 API 한도가 분리된다. 기준일이 하나로 고정된다 |
| 조회 방식 | 런타임에 원천 API 프록시 | 사용자 요청마다 공개 API를 소비한다. 지연이 붙고 서울 쪽은 HTTP 전용이라 중계가 더 필요하다 |
| 조회 방식 | 브라우저에서 원천 직접 호출 | 키 노출, HTTP 전용 엔드포인트, CORS 문제가 동시에 걸린다 |
| 조회 방식 | 검색 엔진·벡터 검색 도입 | 조회는 코호트 키 완전 일치 + 건물명 접두어 검색이다. 인덱스 JSON 하나로 끝난다 |
| 주소·위치 | **자체 문자열 인덱스 (채택)** | 원천에 좌표가 없고 외부 지오코딩 응답을 파이프라인 중간 산물로 저장할 수 없다. 자치구·법정동·건물명 인덱스로 자동완성과 별칭 후보 제시까지 해결하고, 못 찾으면 후보 3개를 보여 주고 사용자가 고르게 한다. 고르지 않으면 판정하지 않는다 |

## 11. 향후 확장 지점

확장을 위해 지금 만들어 두는 것은 없다. 아래는 **그 시점이 왔을 때 어디를 건드리면 되는지**의 기록이다.

1. **전국 확대** — 수집 단계의 법정동코드 목록만 늘린다. 호출량은 코드 수 × 연월 수로 선형 증가하고 개발계정 10,000건/일 안에서 며칠에 나눠 받을 수 있다. 샤딩 축은 자치구 → 시군구로 바뀔 뿐 스키마는 같다. 개발계정 한도가 부족해지는 시점도 여기이며, 그 전에는 운영계정으로 전환할 이유가 없다.
2. **주택 유형 확대** — 연립다세대·오피스텔은 같은 코호트 스키마에 들어간다. 다만 유형별 표본 가용률을 먼저 측정해야 하고, 측정 전에는 그 유형의 분포 판정을 열지 않는다.
3. **별칭 사전의 자산화** — 지자체명·건물명 별칭은 이 제품 밖에서도 쓰인다. 파이프라인 입력 자산으로 분리해 두었으므로 그대로 떼어 낼 수 있다.
4. **스냅샷 간 비교** — manifest에 기준일과 집계 버전이 있으므로, 과거 스냅샷을 보관하면 "지난달 대비 이 코호트가 어떻게 움직였는가"를 추가 수집 없이 계산할 수 있다.
5. **알림과 LLM 교체** — 알림은 서버 상태를 늘리지 않고 표준 캘린더 파일 내보내기로 먼저 해결한다(계정·푸시는 원칙 5를 다시 통과해야 한다). LLM은 호출부가 함수 한 곳이고 `OPENAI_BASE_URL`로 엔드포인트를 바꿀 수 있으며, 검증층은 제공자와 무관하게 동작한다.

## 미확정 항목 (정직하게 남긴다)

1. 서울 OA-21276의 **일일 호출 한도**를 확인하지 못했다. 파이프라인을 재개 가능하게 만드는 것으로 대응했지만, 전체 재구축 소요 일수는 확인 후에야 확정된다.
2. 코호트 개수와 산출물 크기는 측정된 행 수에서 계산한 추정이지 실제 집계 결과가 아니다. 호스팅의 파일 수·크기 한도와 함께 파이프라인 1회 실행 후 실측으로 대체한다.
3. 갱신요구권 필드의 빈 값이 "행사하지 않음"인지 "기록되지 않음"인지는 데이터만으로 구분되지 않는다. 아키텍처는 이 모호성을 해결하지 않고, 화면 문구와 배너로 그대로 전달한다.
