## 2. Why — 아키텍처 원칙

### 원칙 1. 판정은 결정론이다

- **Why**: 판정 6종(법정 기한, 코호트 백분위, 표본 수, 5% 상한 금액과 초과 차액, 신규 시세 대비 차액, 환산 부담)은 전부 산술이다. 같은 입력에 같은 출력이 나와야 사용자가 그 숫자를 협상 자리에 들고 갈 수 있다.
- **무엇·어떻게**: 판정 경로에 LLM을 두지 않는다. LLM은 ① 자연어·붙여넣은 메시지의 구조화 ② 건물명 별칭 후보 제시 ③ 숫자의 재서술 ④ 통지 문안 초안, 네 곳뿐이다. 함수는 프런트엔드가 만든 숫자 딕셔너리를 받아 문장만 돌려주고, 문장 속 숫자가 딕셔너리와 문자열로 일치하지 않으면 그 문장을 버린다.

### 원칙 2. 런타임 외부 의존을 하나로 줄인다

- **Why**: 외부 호출이 늘수록 끊길 지점이 늘고, 공개 API 한도는 사용자 수에 비례해 소진된다.
- **무엇·어떻게**: 런타임 외부 호출은 **OpenAI 하나뿐**이다. 원천 API도 좌표·지도 서비스도 런타임에 호출하지 않는다. OpenAI가 끊겨도 판정은 그대로고 문장만 템플릿으로 바뀐다.

### 원칙 3. 데이터는 빌드타임에 고정한다

- **Why**: 원천은 262만 행이고 갱신은 하루 1회다. 요청마다 다시 계산할 이유가 없다. 기준일을 화면에 못 박으려면 기준일이 배포마다 하나여야 한다.
- **무엇·어떻게**: 수집·정규화·집계는 빌드 파이프라인 안에서 끝난다. `manifest.json` 하나가 기준일·행 수·채움률·집계 버전을 들고, 프런트엔드는 그 값을 상단 배너에 그대로 출력한다.

### 원칙 4. 비밀값은 서버에만 둔다

- **Why**: LLM 키를 브라우저에 두면 그 키는 공개된 것이다. 이 한 가지 이유로 정적 전용 호스팅이 탈락한다.
- **무엇·어떻게**: `OPENAI_API_KEY`는 Functions 런타임 환경변수로만 존재한다. 원천 API 키는 빌드 머신에만 둔다. `.env`는 커밋하지 않고 `.env.sample`만 저장소에 두며, 배포 환경변수는 호스팅 대시보드에서 설정한다.

### 원칙 5. 개인정보는 애초에 받지 않는다

- **Why**: 받지 않은 정보는 유출되지 않고 보관 정책도 필요 없다. 이 제품의 판정에는 개인 식별 정보가 필요 없다.
- **무엇·어떻게**: 입력은 자치구·법정동·건물명·전용면적·만기일·현 보증금·제시 조건뿐이다. 업로드 엔드포인트가 없고, 선택 기록과 알림은 브라우저 로컬에만 남으며, 붙여넣은 임대인 메시지는 구조화 직후 버린다.

### 원칙 6. 데이터가 모르는 것은 모른다고 끝낸다

- **Why**: 원천이 단지 일련번호를 주는 유형은 아파트뿐이라 나머지 세 유형은 같은 건물끼리 비교할 수 없고, 표본이 없는 코호트도 있다. 이 구간에서 추정치를 만들면 제품이 거짓말을 한다.
- **무엇·어떻게**: 집계 자산이 표본 수 `n`을 항상 포함한다. 화면은 `n`을 그대로 적고, `n < 3`이면 판정을 보류하며, 결과 0건은 "판정 불가"로 끝낸다. `n`을 감추는 렌더 경로를 두지 않는다.

## 4. How — 데이터 파이프라인

각 단계는 입력·처리·출력·검증 지점을 갖는다. 검증 지점을 통과하지 못하면 다음 단계로 넘어가지 않는다. 전부 `scripts/build_assets.py` 한 파일이다.

### 단계 1 — 수집

- **입력**: `DATA_GO_KR_SERVICE_KEY`. **Decoding 키를 URL 인코딩해 쓴다** — Encoding 키의 `+` 를 그대로 보내면 `SERVICE_KEY_IS_NOT_REGISTERED_ERROR` 가 난다.
- **처리**: 유형 4종 × 자치구 25개 × 연월 12개 = **1,200 조합**을 `LAWD_CD`(법정동코드 5자리) × `DEAL_YMD` 로 호출한다. 워커 8, 조합당 최대 3회 재시도.
- **출력**: 파싱된 행 596,178개와 `data/raw-rows.json.gz` 캐시. 재집계는 네트워크 없이 `--from-cache` 로 한다.
- **검증**: HTTP 상태와 **응답 본문의 결과코드를 함께** 본다(200 이어도 본문이 오류일 수 있다). 실패 조합과 0건 조합을 목록으로 남기고, 아파트 0건 조합은 이름을 찍는다. **조용히 빠지지 않게 하는 것이 이 단계의 전부다** — 공공 API 를 8워커로 두드리면 429 가 나고, 실제로 오피스텔 80개 조합이 통째로 빠진 채 자산이 만들어진 적이 있다.

### 단계 2 — 전세→전세 갱신 판별

- **Why**(이 필터): 월세가 섞이면 보증금 단독 비교가 성립하지 않는다. 환산해 넣으면 5% 초과 비율이 35~46% 사이에서 흔들린다 — 가정이 결과를 바꾸는 구간이라 **제품이 서 있을 자리가 아니다.**
- **처리**: `계약구분 = 갱신` 이고 종전 보증금이 있고 **종전 월세와 현 월세가 둘 다 비어 있는** 행만 남긴다. 종전이 전세면 종전 월세는 숫자 0 이 아니라 **공백**으로 온다 — 숫자로 읽으면 표본이 통째로 사라진다.
- **출력**: 85,691건.
- **검증**: 인상률이 −90~300% 밖이면 자릿수 사고로 보고 버리고 **버린 건수(61건)를 자산에 남긴다.** 실제 데이터에 `종전 4만원 → 현 48,500만원` 같은 행이 있다.

### 단계 3 — 집계

- **처리**: 코호트 키는 다섯 단계다 — `유형|자치구|법정동|단지|면적대` 부터 `유형|자치구|||` 까지. **단지 단계는 아파트에만 만든다** — 원천이 단지 일련번호를 주는 유형이 아파트뿐이기 때문이다(오피스텔·연립다세대·단독다가구는 596,178행 전부 결측). 코호트마다 정렬된 인상률 벡터(0.01%p 정수), 5% 초과·동률 건수, 같은 코호트 신규 전세 보증금 중앙값과 표본 수를 남긴다.
- **분위수만 담지 않는 이유**: "상위 몇 %"는 전체 순위가 있어야 낼 수 있다. 벡터는 정수라 gzip 이 잘 접는다.
- **5% 초과·동률만 벡터가 아니라 원본 행의 정수 비교 결과를 싣는 이유**: 벡터는 0.01%p 로 접혀 5.0026% 가 5.00% 로 내려앉는다. 실측에서 행사 기록 있는 쪽의 초과가 0.37% → 0.01% 로 바뀌었다. **화면의 판정(R1)과 코호트가 같은 비교를 써야** 같은 계약이 초과이면서 분포에는 없는 일이 생기지 않는다.
- **원본 행은 출력하지 않는다.** 크기 때문이기도 하고, 개별 계약을 자산에서 다시 집어낼 수 없게 하려는 것이기도 하다.
- **출력**: 코호트 11,715개(표본 3건 미만은 싣지 않는다), 단지 색인 5,908개, 서울 전체 앵커.

### 단계 4 — 배포 게이트

- **Why**: 스냅샷은 다시 만들 때마다 화면에 바로 반영된다. **원천이 망가진 날 자동으로 화면에 반영되는 것**이 이 서비스의 가장 큰 단일 위험이다.
- **처리**: 8종을 계산한다 — 코호트 표본, 벡터 정렬, 초과 건수 상한, 중앙값 범위, 전체 표본 하한, 갱신 행의 종전 보증금 결측률, 유형별 갱신요구권 양성 토큰 비율, **직전 스냅샷 대비 그 비율의 낙폭**. 목록과 임계값은 `05-TEST.md` §3.
- **검증**: 하나라도 걸리면 자산을 **쓰지 않고** 중단한다. 배포본은 옛 자산으로 계속 동작한다.

### 단계 5 — 산출물 크기 관리

- **처리**: 코호트를 **자치구 25개 샤드**로 쪼개 사용자가 자기 자치구 하나만 받게 한다. 단지 색인은 같은 샤드에 담아 요청을 1회로 줄인다.
- **검증**: 사용자 1인당 전송량을 실측한다(§6). **콘텐츠 해시는 쓰지 않는다** — 대신 짧은 캐시로 관리한다(§8 캐시 전략).

## 5. How — 런타임 흐름

```text
 사용자              프런트엔드(정적)            Functions            OpenAI
   │ 만기일·주소·금액      │                        │                   │
   ├─────────────────────▶│ manifest / buildings   │                   │
   │                      │ cohorts/<자치구> fetch │  (외부 호출 없음)  │
   │                      │ 판정 6종 계산 ← 여기서 끝                    │
   │◀─────────────────────┤ 숫자·타임라인·배너 렌더 │                   │
   │                      │                        │                   │
   │ "문안 만들어 줘"(선택) │ POST /api/draft        │                   │
   ├─────────────────────▶│ {숫자 딕셔너리, 상황문} │                   │
   │                      ├───────────────────────▶│ 입력 검증 → 호출  │
   │                      │                        ├──────────────────▶│
   │                      │                        │◀──────────────────┤
   │                      │◀───────────────────────┤ 출력 검증 3중      │
   │◀─────────────────────┤ 통과: 문장 / 실패: 템플릿                   │
```

**함수가 하는 일**: 비밀값 보관, OpenAI 호출, 출력 검증층 3중 적용, 실패 시 템플릿 대체.

**함수가 하지 않는 일**:

- 판정 계산을 하지 않는다. 숫자는 이미 프런트엔드가 만들어 보낸 것이다.
- 원천 API를 호출하지 않는다. 사용자 요청과 공개 API 한도를 연결하지 않는다.
- 저장하지 않는다. 데이터베이스가 없고, 요청 본문을 로그에 남기지 않으며, 응답은 `no-store`다.
- 사용자를 식별하지 않는다. 세션도 쿠키도 없다.

**검증층이 세 겹인 이유**: 숫자가 틀리면 협상 자리에서 사용자가 틀린 숫자를 말하게 된다. 법 결론을 쓰면 서비스가 법률 자문이 된다. 입력에 없던 고유명사·날짜·금액이 등장하면 그것은 생성된 사실이다. 세 실패 양상이 서로 달라 한 겹으로는 못 막는다.

## 6. 배포 구성

### Why — Cloudflare Pages + Functions

- **Why**: 정적 호스팅과 서버리스 함수가 한 곳에서 무료이고 콜드스타트가 없다. LLM 키를 브라우저에 노출할 수 없어 함수가 반드시 필요하므로 정적 전용 호스팅은 애초에 후보가 아니다.
- **대안과 트레이드오프**: Vercel 무료 플랜은 기능이 충분하고 개발 경험도 더 매끄럽지만, 무료 플랜이 **비상업 용도로 한정**되어 제품의 장래 성격에 제약을 건다. 성격이 바뀌면 이전 비용이 생긴다.

### What — 산출물 (2026-09-18 실측)

```text
dist/
├── index.html                  화면 하나. 섹션 7개가 같은 판정 딕셔너리를 렌더한다
├── assets/
│   ├── app.css                 토큰 기반. 라이트·다크 두 벌
│   ├── app.js                  입력·모드 판정·렌더·로컬 보관
│   └── rules.js                판정 산술 7종. 순수 함수, 외부 의존 없음
└── data/
    ├── index.json              자치구 목록과 빌드 메타 (1.7KB)
    ├── anchors.json            서울 전체 상수 + 모수 문자열 (1.3KB)
    └── cohort/<자치구>.json × 25   코호트 + 건물 색인. 최대 270KB (gzip 39KB)

functions/
└── api/
    ├── _llm.js                 비밀값·공통 규약·검증층 (밑줄로 시작하면 라우트가 아니다)
    ├── parse.js                POST /api/parse
    └── draft.js                POST /api/draft
```

`functions/` 는 `dist/` 밖에 둔다. Pages 가 프로젝트 루트의 `functions/` 를 라우트로 올린다.

**실측 규모**: 원본 596,178행 → 전세→전세 갱신 85,691건 → 코호트 11,715개 + 건물 색인 5,908개. 자산 합계 3.2MB, **사용자 1인당 전송량은 자치구 샤드 1개 ≈ gzip 40KB**다. §8의 추정(1인당 150KB)보다 작다.

**캐시** (2026-09-18 실측으로 수정): `/assets/*` 는 **`no-cache`** 다. 파일명에 콘텐츠 해시가 없어서 긴 캐시를 걸면 **배포해도 옛 코드가 계속 돈다** — `max-age=3600` 때문에 수정이 한 시간 동안 반영되지 않았고, 브라우저로 확인하지 않았으면 고쳤다고 착각할 자리였다. `index.html` 만 `no-cache` 로 두면 새 HTML이 **같은 이름의 옛 JS**를 가리킨다. 조건부 요청으로 304 를 받는 비용이, 고친 것이 반영되지 않는 것보다 싸다.

데이터 파일은 `/data/*` 로 묶어 같은 주기(600초)를 준다. 앵커만 새로 받고 코호트가 낡으면 화면의 두 숫자가 서로 다른 기준일을 가리킨다.

### How — 환경변수

| 이름 | 어디에 두는가 | 필수 | 용도 |
|---|---|---|---|
| `OPENAI_API_KEY` | 호스팅 대시보드(런타임) | 필수 | 문장 생성 |
| `OPENAI_MODEL` | 호스팅 대시보드(런타임) | 선택 | 모델 고정 |
| `OPENAI_BASE_URL` | 호스팅 대시보드(런타임) | 선택 | 프록시·대체 엔드포인트 경유 |
| `DATA_GO_KR_SERVICE_KEY` | 빌드 머신 `.env`만 | 빌드 필수 | 국토부 수집. **Decoding 키를 URL 인코딩해 쓴다** |
| `SEOUL_OPEN_DATA_KEY` | 빌드 머신 `.env`만 | 빌드 필수 | 서울 수집 |

원천 API 키를 배포 환경에 넣지 않는 이유는 단순하다 — 런타임이 원천을 호출하지 않으므로 필요 없기 때문이다. 필요 없는 비밀값은 두지 않는다.

### 배포 절차

```bash
set -a; . ./.env; set +a
./scripts/test_all.sh                        # 키 없이 도는 검증 전부 (약 3초)
python3 scripts/build_assets.py              # 수집 → 집계 → 자산 게이트 → dist/data (약 3분)
npx wrangler pages dev dist                  # 로컬 확인. 함수 포함
npx wrangler pages deploy dist               # 배포
```

1. `manifest`/`anchors.json` 의 기준일이 바뀌었는지 확인한다. 그대로면 데이터가 갱신되지 않은 것이다.
2. 수집 로그의 `실패 N` 이 0인지 본다. 0이 아니면 `--retry` 로 그 조합만 다시 받는다. **429는 조용히 빠진다** — 실측에서 오피스텔 80개 조합(7개 자치구)이 통째로 누락된 채 자산이 만들어졌다.
3. 배포 후 확인 2개: 상단 배너의 기준일, `/api/draft` 가 키 없이도 `ok:true` 로 응답하는지.

## 7. 보안

**Why**: 이 제품이 지킬 것은 개인정보가 아니라 **남이 우리 키를 쓰지 못하게 하는 것**이다. 수집하는 개인정보가 없으므로(§7 첫 항목) 위험의 무게중심이 그쪽으로 옮겨 간다.

- **비밀값 관리**: `.env`는 커밋하지 않고 `.env.sample`만 저장소에 둔다. 샘플에는 값이 아니라 발급처와 주의사항을 적는다. 배포 환경변수는 호스팅 대시보드에서 설정하고 저장소에 사본을 두지 않는다.
- **저장소에 넣지 않는 것**: `.env`, 원본 CSV/XML(`data/raw/`), 대용량 압축 파일, 내부 리서치 문서. 재현은 스크립트로 한다.
- **개인정보 미수집**: 입력 항목에 개인 식별 정보가 없다. 업로드 기능이 없다. 선택 기록·알림은 브라우저 로컬에만 남고 내보내기는 사용자가 실행한다. 붙여넣은 임대인 메시지는 구조화 직후 폐기한다.
- **외부 호출 경계**: 런타임 아웃바운드는 OpenAI 한 곳뿐이다. 함수로 나가는 요청 본문은 **코드가 만든 숫자와 사용자가 스스로 붙여넣은 텍스트**이며, 그 안에 식별 정보를 넣지 않는다. 좌표·지도 서비스는 쓰지 않으므로 그쪽 응답 저장 문제 자체가 발생하지 않는다.
- **입출력 검증**: 함수는 본문 크기 상한·필드 화이트리스트·숫자 타입 검사를 통과하지 못한 요청을 거부하고, 응답은 텍스트 한 덩어리로만 내보내 HTML을 그대로 삽입하지 않는다. 신뢰 경계의 검증은 간소화 대상이 아니다.

## 8. 용량과 성능

**Why**: 총량이 아니라 **사용자 1인당 전송량**이 이 아키텍처를 고른 이유다. 원본 59만 행을 그대로 올렸다면 정적 호스팅이 성립하지 않는다.

### 집계 자산 크기

> **아래 표는 빌드 전에 세운 추정이다.** 실측은 §6 에 있고 더 작다 — 자산 합계 3.2MB, 사용자 1인당 자치구 샤드 1개 ≈ **gzip 40KB**. 추정을 지우지 않는 이유는 어긋난 폭이 다음 추정의 보정값이기 때문이다.

#### 빌드 전 추정 (측정된 행 수에서 계산)

| 자산 | 산정 근거 | 추정 크기 | 전송(gzip 추정) |
|---|---|---|---|
| `cohorts/<자치구>.json` × 25 | 코호트 레코드는 키 + 분위수 5개 + 비율 3개 + 표본 수 몇 개 = 200~300B. 자치구당 1,000~1,500 코호트 가정 | 샤드당 0.2~0.4MB | 샤드당 60~100KB |
| `index/buildings.json` | 서울 아파트·연립 건물명 수천 개 × 약 40B | 0.2~0.3MB | 60~80KB |
| `anchors.json` | 서울 전체 상수 수십 개 | 수 KB | 수 KB |
| 합계(배포물 기준) | 25개 샤드 + 인덱스 + 앵커 | 5~10MB | 사용자 1인당 **1샤드 + 인덱스 ≈ 150KB** |

핵심은 총량이 아니라 **1인당 전송량**이다. 사용자는 자기 자치구 샤드 하나만 받는다. 원본 262만 행을 그대로 올렸다면 이 수치는 성립하지 않는다.

### 호출 한도와 소진 계산

| 원천 | 한도 | 전체 재구축 | 일일 증분 | 여유 |
|---|---|---|---|---|
| 국토부 15126474 | 개발계정 10,000건/일 | 서울 25개 법정동코드 × 24개월 = 600회(페이지 포함 최대 약 1,200회) | 25개 코드 × 최근 2개월 = 50회 | 재구축도 하루 한도의 12% 이내 |
| 서울 OA-21276 | 1,000행/호출, 매일 1회 갱신 | 262만 행 ÷ 1,000 = 약 2,623회 | 최근 접수분만 | 일일 호출 한도는 **미확인** → 파이프라인을 재개 가능하게 만들어 며칠에 걸쳐 나눠 받을 수 있게 한다 |

런타임은 원천을 호출하지 않으므로 **사용자 수가 늘어도 공개 API 한도는 소진되지 않는다.** 이 성질이 이 아키텍처를 고른 가장 실질적인 이유다.

### 캐시 전략

- **`/assets/*`: `no-cache`.** 파일명에 해시가 없으므로 긴 캐시는 배포를 무효로 만든다(§6 참조).
- **`/data/*`: `max-age=600`.** 앵커와 코호트를 같은 주기로 묶어 기준일이 갈리지 않게 한다.
- `index.html`: `no-cache`. `og.png`: 1시간(내용이 바뀌면 배포와 함께 바뀐다).
- `/api/draft`·`/api/parse` 응답: `no-store`. 생성 문장은 사용자별로 다르고, 캐시할 이유도 없다.

## 9-2. 구현하면서 바꾼 결정 (2026-09-18~19)

<!-- 프레임워크밖:기록 — 2026-09-18~19 에 바꾼 것의 일지. 결정 자체는 02-SPEC 본문에 반영돼 있다. -->

되돌릴 수 있는 결정이라 분기 문서를 만들지 않고 이유만 남긴다. **결정 자체는 `02-SPEC.md` 본문에 반영돼 있다** — 명세와 구현이 갈린 채로 두지 않는다. (2026-09-19 에 `README.md` 에서 이 문서로 옮겼다. 내용은 그대로다.)

1. **코호트 자산은 분위수 대신 정렬된 인상률 벡터를 싣는다.** 분위수만 담으면 "상위 몇 %"를 정확히 낼 수 없다. 5% 초과·동률 건수만은 벡터가 아니라 **원본 행의 정수 비교 결과**를 따로 싣는다 — 인상률을 0.01%p 정수로 접으면 5.0026% 같은 계약이 정확히 5.00%로 내려앉아, 행사 기록 있는 쪽의 5% 초과가 0.37%에서 0.01%로 바뀐다.
2. **폴백 사다리에 "단지 전체 면적" 단계를 넣어 5단계로 한다.** 단지·면적대 → 단지 전체 → 법정동·면적대 → 법정동 → 자치구.
3. **문안 생성에서 언어 모델은 숫자가 든 문장을 만들지 않는다.** 인사말과 맺음말만 쓰고, 숫자 문장은 전부 브라우저의 코드가 쓴다. 모델에게 재서술을 맡겼더니 숫자가 맞는데 라벨이 바뀌었다 — 코호트 전체 316건을 "행사 기록이 있는 316건"으로, 5% 상한액을 "제시된 보증금"으로 썼다. 숫자 화이트리스트로는 잡히지 않는 오류라 검증 대신 경로를 끊었다. 그래서 검증도 단순해졌다: 모델이 쓴 문장에 숫자나 금액 표현이 있으면 버린다. 한글 수사를 전부 잡지는 않는다 — "이 글"·"만나서"의 이·만까지 걸면 정상 인사말이 한 줄도 남지 않아서, 단위에 붙은 금액 표현만 본다.
4. **서울 밖(M-01)에서도 5% 상한 금액과 인상률은 보여 준다.** 분포 숫자가 아니라 입력값만으로 되는 산술이고, 5% 상한은 지역과 무관한 법정 기준이다.
5. **자릿수 사고를 코호트로 되묻는다(M-11).** 금액이 10배 틀려도 종전과 제시가 같은 배율이면 인상률이 정상이라 어떤 비율 검사도 통과한다. 바깥 기준이 필요해서 같은 코호트의 신규 전세 보증금 중앙값과 대조하고, 1/3~3배 밖이면 **판정을 멈추고 되묻는다.** 버리는 것이 아니라 되묻는 것이다 — 사용자가 맞다고 하면 그대로 판정한다.
6. **`/assets/*` 는 `no-cache` 다.** 파일명에 콘텐츠 해시가 없어서 긴 캐시를 걸면 배포한 수정이 반영되지 않는다(실측: `max-age=3600` 으로 한 시간).
7. **서울시 OA-21276(262만 행) 수집은 이번 빌드에서 뺐다.** 일일 호출 한도가 미확인이고, 코호트 분포는 국토부 4종만으로 나온다. 원천이 하나이므로 별칭 사전·출처 병합·중복 묶음 판정도 만들지 않았다.
8. **단지 단위 비교는 아파트에만 한다.** 원천이 단지 일련번호를 주는 유형이 아파트뿐이다 — 오피스텔·연립다세대·단독다가구는 596,178행 전부 비어 있다. 명세 초안은 오피스텔도 단지 단위로 잡았는데, 그러면 건물명 칸이 뜨고 자동완성 목록은 비어 있고 이름을 치면 판정이 막힌다. **원천에 없는 것을 있다고 가정하면 그 대가는 사용자가 치른다.**
9. **환산 전환율 분포를 상수로 두지 않는다.** 판정 산술과 같은 빌드에서 나온 `anchors.convert` 를 읽는다. 상수로 두면 다른 두 분포와 기준일·모수가 조용히 갈린다.
10. **정형 문장은 언어 모델을 부르지 않고 브라우저에서 읽는다.** `"전세 3억5천인데 3억8천으로"` 같은 문장은 산술로 읽힌다. 규칙 파서(`rules.js` `readAmounts`)가 먼저 보고, 읽으면 **원문이 서버로 나가지 않는다.** 읽지 못하면 `/api/parse` 로 넘긴다. 합격 기준은 처리율이 아니라 **조용한 오수락 0건**이다 — 골든셋의 모든 문장에서 "정확한 값" 또는 "읽지 않음" 둘 중 하나여야 한다. 문법을 좁게 둔 이유가 그것이다(한글 수사·역순·금액 하나는 읽지 않는다).

## 11. 향후 확장 지점

<!-- 프레임워크밖:부재 — 아직 만들지 않은 것의 목록. -->

확장을 위해 지금 만들어 두는 것은 없다. 아래는 **그 시점이 왔을 때 어디를 건드리면 되는지**의 기록이다.

1. **전국 확대** — 수집 단계의 법정동코드 목록만 늘린다. 호출량은 코드 수 × 연월 수로 선형 증가하고 개발계정 10,000건/일 안에서 며칠에 나눠 받을 수 있다. 샤딩 축은 자치구 → 시군구로 바뀔 뿐 스키마는 같다. 개발계정 한도가 부족해지는 시점도 여기이며, 그 전에는 운영계정으로 전환할 이유가 없다.
2. **주택 유형 확대** — 연립다세대·오피스텔은 같은 코호트 스키마에 들어간다. 다만 유형별 표본 가용률을 먼저 측정해야 하고, 측정 전에는 그 유형의 분포 판정을 열지 않는다.
3. **별칭 사전의 자산화** — 지자체명·건물명 별칭은 이 제품 밖에서도 쓰인다. 파이프라인 입력 자산으로 분리해 두었으므로 그대로 떼어 낼 수 있다.
4. **스냅샷 간 비교** — manifest에 기준일과 집계 버전이 있으므로, 과거 스냅샷을 보관하면 "지난달 대비 이 코호트가 어떻게 움직였는가"를 추가 수집 없이 계산할 수 있다.
5. **알림과 LLM 교체** — 알림은 서버 상태를 늘리지 않고 표준 캘린더 파일 내보내기로 먼저 해결한다(계정·푸시는 원칙 5를 다시 통과해야 한다). LLM은 호출부가 함수 한 곳이고 `OPENAI_BASE_URL`로 엔드포인트를 바꿀 수 있으며, 검증층은 제공자와 무관하게 동작한다.

## 미확정 항목 (정직하게 남긴다)

1. 서울 OA-21276의 **일일 호출 한도**를 확인하지 못했다. 파이프라인을 재개 가능하게 만드는 것으로 대응했지만, 전체 재구축 소요 일수는 확인 후에야 확정된다.
